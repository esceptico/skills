# Interface writing

Use this for visible product language: navigation, buttons, feature names, settings, onboarding, status, warnings, errors, and recovery.

## Make language do interface work

- Name things for what people understand or accomplish, not for internal architecture or brand cleverness. Clarity and trust come before personality.
- Prefer direct, specific verbs for actions and concrete nouns for destinations. Make labels predict the result.
- Remove greetings, hedges, filler, and repeated context when they add no meaning.
- Lead with the benefit or reason when it helps someone decide; then state the requested action or consequence.
- Put the most important information first. Keep supporting explanation close to the choice it affects.
- Use one term for one concept across navigation, buttons, settings, help, notifications, and system integrations. Maintain a short product word list when drift is likely.
- Match the tone to the moment. Errors and destructive warnings need calm specificity; completion can be warm but should not interrupt routine work.

## Evaluate names and copy

- Read the text in its real interface, not in isolation. Check nearby labels, hierarchy, truncation, repeated words, and whether the visual design already communicates part of the message.
- Test a feature name as navigation, a button, a setting, a notification, and spoken output where those surfaces apply.
- Check that translation, longer strings, right-to-left layout, pluralization, and grammatical variation do not change the intended meaning or break the interface.
- Remove text that teaches platform basics. If copy is required to explain an unfamiliar control, first consider repairing the control or mapping.
- For errors, state what happened, preserve entered work, and give a specific recovery action. Do not blame the person or expose implementation jargon.
